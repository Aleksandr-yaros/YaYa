# ЯЯ — единый репозиторий проекта компании «Ярос»

Этот репозиторий является главным источником истины по проекту **ЯЯ**.

## Канонический вход в фабрику

Текущий единый канон фабрики цифровых сотрудников:

- `docs/YAYA_FACTORY_UNIFIED_CANON_V10.md` — ЯЯ·ФАБРИКА v10;
- `docs/LOGOS_FABRIC_V10_FUNCTION_ARCHITECTURE.md` — архитектурное ядро;
- `docs/LOGOS_FABRIC_COMMAND_LANGUAGE_CANON.md` — язык команд.

Исторические версии и продуктовые ветки сохраняются как история эволюции, но не должны подменять текущий канон фабрики.

## Как обращаться к проекту

Следующие обращения считаются вызовом одного проекта:

- `ЯЯ`;
- `я-я`;
- `Где я?`;
- `боты ЯЯ`;
- `фабрика ЯЯ`;
- `ЯЯ·ФАБРИКА`;
- `цифровые сотрудники Ярос`;
- `LOGOS_ЦЕНТР`;
- `LOGOS·FABRIC`;
- `ГАУХАР·FACTORYOS`.

На такой запрос агент должен:

1. Проверить актуальные файлы и ветки GitHub.
2. Показать последнюю каноническую версию и статус.
3. Показать архитектуру и эталонный контур CALL-001.
4. Отделить реализованное, прототип и план.
5. Показать риски C/E, незавершённые блоки и следующий шаг.
6. Не отвечать только по памяти, когда доступен репозиторий.

## Команды

- `Где я?` — полный прозрачный статус проекта.
- `Достань фабрику ЯЯ` — единый канон и последнее ТЗ.
- `Создай бота ЯЯ <цель>` — создать безопасный BotSpec Draft.
- `Апгрейд ЯЯ <изменение>` — подготовить новую версию, diff, C/E, dry-run и rollback.
- `Покажи бота ЯЯ <имя>` — показать паспорт цифрового сотрудника.
- `Стоп. Проверь рамку.` — проверить цель, источники, полномочия и границы.
- `Сохрани ЯЯ` — версионировать результат в GitHub.

## Неподвижные правила

- Компания называется только **«Ярос»**.
- AI не имеет права самостоятельной продуктивной записи.
- Демо не подключается к живым данным без отдельного разрешения.
- Для C2–C4 обязательны SPEC·GUARD, dry-run, подтверждение, Commit Boundary, Evidence Ledger, IMPACT и rollback.
- Секреты хранятся только в защищённом хранилище и отображаются masked.
- Исторические документы не удаляются молча; противоречия помечаются как superseded.

## Правило сохранения

Каждое существенное изменение должно:

1. Получить версию `MAJOR.MINOR.PATCH`.
2. Иметь владельца, дату, статус и источник решения.
3. Фиксировать C/E, доказательства, критерии приёмки и rollback.
4. Обновлять `docs/INDEX.md` и канонический файл проекта.
5. Подтверждаться commit и, для крупных изменений, pull request.
